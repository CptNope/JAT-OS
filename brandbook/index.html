Brand foundation

JAT OS turns a WordPress site into a desktop environment people can step into and out of. It is a working layer for real tools, not a novelty skin, and the website underneath always stays the website.

Mission, vision and positioning

Mission
Give independently built web apps one coherent place to work side by side, with windows, a launcher and settings that behave the way people already expect from a desktop, without asking the host website to give anything up.
Vision
A portable desktop environment for the open web. It starts inside WordPress, is built so it can stand on its own, and lets any well-described web app join the workspace while keeping its own boundaries.
Positioning
JAT OS is a modular operating layer delivered as a WordPress plugin. It unifies a family of independently hosted PWAs, including apps that cannot be embedded, under one shell, one design system and one permission-controlled app registry, while the host site's pages, permalinks, SEO, theme and block editor stay untouched.

Product philosophy

Five principles settle disagreements. When two of them pull apart, the earlier one wins.

  1. The website comes first; the OS is an opt-in layer. Entering OS mode never compromises the site's content, URLs, SEO, theme or editor, and leaving is always one clear action away.
  2. One coherent shell around honest app boundaries. Apps look and behave like one family. The shell never hides real limits: an app that can't be embedded, an offline gap, separate storage.
  3. Specify before simulating. Every control does something that has been specified. Concepts are labeled as concepts and future capabilities are named as future.
  4. Adapt to the device, don't shrink. Each class of device and input method gets a layout and an interaction model that fits it.
  5. Portable by construction. The shell, tokens and components stay independent of WordPress so JAT OS can become a standalone platform.

Logo and identity

The mark is two rounded windows. The outlined back window sits top right, the filled front window bottom left with its title strip. Read together, the back window's right edge is the stem of a J and the front window is its bowl: the company initial, made from the product's own object.

Clear space and minimum size

Clear space is twice the height of the front window's title strip: 16 units of the 64-unit grid, a quarter of the mark's height, on every side. Nothing enters it: no text, edge, other logo or busy image.

Correct and incorrect usage

  • Full color on a light, quiet ground

  • Reversed on a dark ground

  • On a wallpaper, on a solid plate

  • Don't stretch or squash

  • Don't recolor

  • Don't rotate

  • Don't add glows, shadows or effects

  • Don't mirror or rearrange the windows

  • Don't set it on a busy wallpaper without a plate

Wallpaper-dependent contrast

People choose their own wallpaper, so nothing that carries meaning may depend on it.

  • Desktop labels are always --desktop-label white with --desktop-label-shadow. The shadow is what keeps them legible on light wallpapers like Ridge Day, where white alone measures 1.45:1.
  • Bars (menu bar, taskbar, dock, shelf) use --chrome-bar with backdrop-filter: blur(var(--chrome-blur)), 24 px. Translucency is only legible because the blur flattens what's behind it.
  • Solid fallback. Under prefers-reduced-transparency: reduce, the token file swaps --chrome-bar for --chrome-bar-solid and sets the blur to 0. Where backdrop-filter is unsupported, use @supports not (backdrop-filter: blur(1px)) to do the same.
  • Windows, menus and dialogs are always opaque. Only bars and menus may blur; windows never do.

Usage rules

  • Accent is for action and state only: primary buttons, selection, focus, checked controls, the highlighted menu item and progress. It never decorates headings, borders or empty space.
  • One primary action per view. If two things are blue, one of them is wrong.
  • Brand is for identity. --brand appears in the logo and brand moments such as the welcome screen. It is never a button fill; use --accent.
  • App colors are for app tiles only. VectorCraft purple never signals "selected", and a red FigCraft tile never signals an error. State always comes from the semantic tokens.
  • Status colors come with words or icons. A red dot alone is not an error message. Color is never the only signal.
  • Dark is designed, not inverted. Dark surfaces step up in lightness as they rise; shadows deepen and windows gain a 1 px light hairline instead of relying on shadow alone.

JetBrains Mono 400 and 500 at 0.92em of the surrounding text, for code, token names, paths, URLs, file sizes in inspectors and keyboard keys. Never for labels, headings or decoration.

Truncation, numerals and responsive rules

  • Never truncate a button. If a label doesn't fit, rewrite it shorter or let the button wrap to its own line.
  • Never truncate in the middle of a file extension for file names; truncate the stem and keep .pdf visible where space allows.
  • Phones (under 600 px): body text and inputs are 16 px (also prevents mobile browsers zooming on focus); menu rows grow to 44 px; section headings step down one size, for example --text-3xl to --text-2xl.
  • Respect user font size. All type tokens are in rem, so the browser's font-size setting scales the whole interface; layouts must survive 200% text zoom.

Performance rules

  • Windows animate transform and opacity only. Width, height, top and left change once, at the end of a move or resize.
  • Never animate blur. backdrop-filter is static and limited to bars, menus and popovers; windows and their contents are opaque.
  • 60 fps budget: 16 ms per frame during drags. Pointer moves are read in pointermove and applied in one requestAnimationFrame; no layout reads during a drag.
  • Iframes are expensive. During drags and resizes, frames get pointer-events: none; minimized windows keep their frame alive but hidden with visibility, never re-created.
  • One moment at a time. No staggered grids, no idle animation, no parallax on wallpapers.

Screen reader rules

  • Windows are role="dialog" without aria-modal, labeled with the app name (aria-label="VectorCraft"). The iframe inside gets a title with the same name.

App ecosystem

Apps are independent websites described by a manifest in the JAT registry. The OS gives them a window, a place in the launcher and a consistent frame; it does not give them each other's data.

Independently hosted apps never share storage, permissions or service-worker control with the OS automatically. Each app keeps its own origin, its own storage and its own service worker. Anything shared goes through an explicit, permission-scoped bridge message.

The jat-bridge/1 protocol Planned

A draft for integrated apps. It runs over window.postMessage between the OS and an app's iframe; nothing about it is required for embedded or external apps.

Envelope

{
  "jat": "1",                       // protocol major version
  "id": "c7f3a1e2-…",               // unique per message; replies reuse it
  "type": "jat:permission.request", // namespaced message type
  "payload": { … }                  // type-specific body
}

Handshake

  1. The OS loads the app's iframe and, on load, posts jat:hello to the frame with targetOrigin set to the registry origin: {"payload": {"nonce": "…", "os": "1.0", "theme": "dark", "shell": "dock"}}.
  2. The app replies to event.origin with jat:ready: {"payload": {"nonce": "…", "manifestId": "com.jeremyandersontech.vectorcraft", "bridge": "jat-bridge/1"}}.
  3. The OS accepts the reply only if its origin equals the origin of the registered launch.url, the nonce matches and manifestId equals the registry entry. Otherwise the app is treated as plain embedded and the attempt is logged.
  4. After 5 s without jat:ready, the OS stops listening for that frame.

Origin verification

  • Every inbound message is checked: event.source must be that app's frame and event.origin must equal new URL(launch.url).origin. Mismatches are dropped silently.
  • Outbound messages always name the exact target origin, never "*".
  • Navigation away from the registered origin ends the session; a new handshake is required.

Permissions

An app asks with jat:permission.request and {"permissions": ["notifications"], "reason": "Tell you when an export finishes"}. Only permissions listed in its manifest can be requested. The OS shows a prompt naming the app and its origin, then replies with jat:permission.result: {"granted": ["notifications"], "denied": []}. Grants are per user and per app, revocable in Settings, and never inherited by other apps on the same origin.

A failed request is answered with jat:error carrying the request's id and {"code": "E_PERMISSION_DENIED", "message": "notifications was not granted"}. Codes: E_ORIGIN, E_HANDSHAKE, E_PERMISSION_DENIED, E_NOT_DECLARED (permission missing from the manifest), E_UNSUPPORTED_TYPE, E_BAD_PAYLOAD, E_VERSION, E_TIMEOUT. Messages are for developers; the OS writes its own user-facing copy.

Versioning

  • The envelope's jat field is the major version. Additive changes (new types, new optional fields) keep the major version; anything else increments it.
  • Unknown types get E_UNSUPPORTED_TYPE; unknown fields are ignored.
  • The OS supports the current and previous major version for at least 12 months after a new one ships.

WordPress integration

  • Isolation both ways. The /os/ template enqueues only the shell's own CSS and JS and skips wp_head output from the theme. Inside, the Shadow DOM keeps any stray site CSS out and the shell's CSS in.

Content Security Policy and iframes

  • The /os/ response sets frame-src to the origins of registered embedded and integrated apps, generated from the registry: Content-Security-Policy: frame-src https://cptnope.github.io; …
  • If the WordPress site already sends its own CSP (from a security plugin or the server), it must also allow those app origins in frame-src, or every embedded app falls back to a new tab.
  • Each app controls whether it can be framed through its own X-Frame-Options and frame-ancestors. The OS can't override that and must detect refusal (load timeout plus a securitypolicyviolation report where available) and show the fallback.
  • Iframes always carry the sandbox list above, allow only for features the app's manifest declares and the person has granted, and referrerpolicy="strict-origin-when-cross-origin".

Service-worker scope

  • Each app keeps its own service worker in its own scope on its own origin (for the Craft apps, https://cptnope.github.io/<app>/). The OS records the scope in the manifest; it never registers, updates or unregisters it.
  • If the OS gets a service worker of its own, its scope is /os/ and nothing wider, so it can never intercept the website's pages or any app path.
  • "Works offline" in the OS means only what each app's own worker provides. The OS says which apps declare "offline": "app-managed" and never promises more.
